### 为什么没有一张卡叫「番茄钟」

番茄工作法是一套**预设值**（专注 25 / 短休 5 / 每 4 段长休 15），不是一种计时机制 ——
它的机制就是"倒计时 + 到点自动切段"，那正是「间歇计时」。给一套预设单独发一张卡，
卡片的功能承诺就超过了它实际保证的范围：用户会以为它默认 25/5、能数番茄、四个一循环，
而这些都不该由一张工作台卡片来担保。所以它是**间歇计时里的一个预设**：
要 50/10、90/15 也是改预设表的一行，不用再发一张卡。

这个判断同时也修正了本文档早先的排序 —— 原来的写法把「番茄钟」当成"最贵、最该最后做"的卡，
而实际上它是**最便宜**的：机制与倒计时共用，只差一个相位表。

### 一套机制，四种投影

四个钟共用 `RunState = { running, startedAt, accumulatedMs }`，其余全是它的投影：
正计时直接显示 `elapsed`；倒计时显示 `duration - elapsed`；间歇与呼吸是"倒计时 + 到点换一段"。

**硬纪律：不存累加计数器，存"从哪个时刻开始的"。**
`setInterval(1000)` 每秒 `acc += 1000` 在后台标签页会被节流到一分钟一次，
于是它记的时间比真实时间少一大截 —— 用户回来发现"我明明过了十分钟"。
`setInterval` 只用来重绘，不用来累加时间。

### 月度热力图：颜色是相对深浅，不是好坏

- 按**本月**最大值归一，且 max 至少为 1（不除以零）。
- **上个月的极端值不得影响本月色阶** —— 早先的写法是对整份数据求 max，
  结果是"9 月某个 99"把 10 月压成一片浅色，而界面上没有任何地方能解释这件事。
- **只有最大值为 1 时才退化成两档**（所有非零值都是 1，"填满 vs 空着"已经是全部信息）。
  `{1, 4}` 是真有两个量级，这时必须画出差。
- 未来的日子画得更淡、不上色：还没到的日子不该显示成"没打卡"。
- 图例上明写「颜色按本月相对深浅，不是好坏」。**颜色带评价色彩，
  而"这天打了三次卡"既不是好也不是坏** —— 那个评价不该由一张卡替用户下。
- 刻意**不做一整年 53 列**：那在这个工作台里会挤成一条 1px 的线，投影也救不了。

### 快捷链接：只做复制，不做打开

要在桌面壳里打开外部链接需要 `tauri-plugin-opener` —— 那是这个项目至今**唯一没引入的新依赖**，
而且它把"链接去哪"交给外部应用决定。权衡之后只做复制：不需要新依赖、行为完全可预期、
网页版与桌面版一致。代价是多一步 Ctrl+V，所以每个条目都写明"点了会复制什么"。
协议用**白名单**（http/https/mailto/ftp/obsidian/vscode/file），黑名单永远漏得掉下一个危险协议。

### 整数位计算：率的解读按数值大小，不看写法

- `>= 1` 已经是百分数（`6` = 6%），`< 1` 是小数（`0.06` = 6%），带不带 `%` 等价。
- 早先的写法是"不带小数点就乘 100"，那会把 `6` 读成 **600%** —— 在税率场景里差 100 倍，
  而界面看不出错在哪。这条是本轮测试逼出来的设计修正。
- 金额到**分**、率到**万分之一**（税点 6%、折扣 2.5%、分摊到 3 位都要四位精度）。
- 四舍五入用**财务口径（负数远离零）**而不是 `Math.round`：后者给 `-0`（往 +∞ 取整），
  那种差异会让一张退款单和一张发票对不上。
- 去率净额用**除法**而不是 `base - result`：后者会被四舍五入误差放大。

### 值班表：一条可手算的规则，不做可配置排班

可配置的排班规则（每人一条正则式）才是真正的排班系统，也是最容易出错的软件。
这一版只支持一条：**从锚点起按天序轮转，同日内按班次顺延**
（索引 = `(天数 × 每天班次数 + 班次序号) mod 名单长度`）。它覆盖绝大多数小团队的轮流值日，
而且任何一天的值都能手算验证。名单为空时显示「待排」，**不回落到第一个人** ——
那会让一张没填的表看起来像已经排好了。需要复杂规则时正解是接一个日历系统。

- 12 个月**只在展开视图里**渲染，概览视图走 2 列摘要 —— 拖到最小尺寸时不会带着 500 个节点跑。

- 闰年、大小月、跨年周全部按真实日历规则算，**不假设每月 30 天**。
- `daysInMonthOf` 复用 `heatmap` 已有的那份实现。起初在年历里又写了一遍，
  被 `export *` 的重名冲突顶出来才发现 —— 大小月与世纪年只能有一套算法，
  两份迟早会走偏。世纪年（1900 平 / 2000 闰）的断言也一并搬进 heatmap 的单测。
- 不做"点某天写备注"：那要求用户先有一个能记东西的地方，而这张卡的定位是**看全年分布**。

代价是：要在年历上直接标注，还是得等便签/待办长出日期维度。所以这张卡刻意只读。

### 每日一图：把 CORS 问题挪到桌面侧，而不是找一个"能用的第三方接口"

当初跳过的理由是"CSP 不能动态加域名"。重看之后发现卡住的是**取数方式**，不是这张卡本身：

- Bing 的 `HPImageArchive.aspx` 不返回 `Access-Control-Allow-Origin`，WebView2 的前端 `fetch`
  **必然**被拦。试过的社区接口（oioweb / thinkercn / vvhan / moing）在本机分别 TLS 失败、
  DNS 失败、超时；Wikimedia 的官方接口在本机也超时。依赖它们等于把一张卡做成随机故障。
- 取数改由桌面侧发：新增 `web::bing_daily` 命令，**Windows 上直接用系统自带的 WinHTTP**
  （`#[link(name = "winhttp")]`，不引入任何新 crate）。
  曾经试过加 `reqwest` 依赖 —— 那会让链接产物大出一个量级，见下面「未解决的那一半」。
- `<img src>` 的加载**不受 CORS 约束**，所以拿到地址直接渲染即可：CSP 只需在 `img-src`
  放行 `https://www.bing.com` 一个域名，`connect-src` **刻意不放行** —— 前端已经没有任何理由
  直连 bing，多开一个源只是多一个可被打的面。`tests/release/csp.test.ts` 把正反两面都钉住了。
- 超时 10s（WinHTTP 默认 connect 是 60s，对一张卡片太久），状态码非 200 直接报错。
  **"取不到"必须和"今天没图"在界面上分得开**，否则用户没法判断该不该点刷新。
- 句柄用 RAII 收：WinHTTP 的 `HINTERNET` 不会自动释放，漏一次就是内核句柄泄漏。

代价与边界：这是一张**只读、只读一个固定来源**的卡。不能换源，也不能查任意网址 —— 那正是下一节的事。

### 曾记为「未解决」：`cargo test` 在这台机器上跑不起来（2026-10-06 已修）

当时的记录是：lib 引用 `web` 模块后测试二进制就加载失败，

```
exit code: 0xC0000139, STATUS_ENTRYPOINT_NOT_FOUND
```

排除过的原因（每一项都实测过）：

| 怀疑 | 当时的实测结果 | 2026-10-06 复核 |
|---|---|---|
| 二进制太大 | 98.9 MB 也失败、119 MB 通过，非单调 | 无关 |
| 完整 DWARF 调试信息 | 加 `[profile.test] debug = 1` 压到 98.9 MB，仍失败 | 无关 |
| incremental 编译 | `CARGO_INCREMENTAL=0` 仍失败 | 无关 |
| **静态导入解析不了** | 用 ctypes 逐个导入验证：**全部可解析** | **就是它，但那次验证漏了它** |
| `WebView2Loader.dll` 不在 `deps/` | 复制过去后仍失败 | 无关（它是 KnownDLL，拷贝本就无效） |
| mingw 在 PATH 上版本冲突 | 去掉 PATH 仍失败 | 无关 |
| 产物损坏 | `cargo clean -p modulo` 后完整重编，仍失败 | 无关 |

**当时的结论错了。** 原文写的是「本机环境级问题，根因未定位，从项目侧改不动，需要另一台机器来验证」——
实际上就是项目侧一个缺失的应用清单。真正的链条：

```
tauri → muda → windows crate → 测试壳静态导入 comctl32.dll::TaskDialogIndirect
```

`TaskDialogIndirect` 只由 **comctl32 v6** 导出，System32 的 v5 存根不导出。绑到 v6 的唯一途径是
应用清单声明 `Microsoft.Windows.Common-Controls 6`（SxS 旁加载），而 `tauri-build` 生成的
`resource.rc` 里**本来就有**那段清单 —— 只是它只把资源链给了 bin 目标
（发的是 `cargo:rustc-link-arg-bins=`）。测试壳因此缺清单 → 绑 v5 → 缺入口 → 起不来。

那次 ctypes 验证为什么漏：`TaskDialogIndirect` 是静态导入项，而逐个 `ctypes` 试的是**按需**
`LoadLibrary`/`GetProcAddress` 的路径，两条路径的绑定结果不一样。

修法与排除掉的两个想当然做法见 `src-tauri/build.rs` 的注释。现在本机 `cargo test` 直接可跑。

### 网页监控（第 41 张卡）：做，但把边界定死

当初跳过它的理由是 SSRF：任意 URL 的网页监控必须回答「服务器替谁去访问了这个地址」。
重看之后发现卡住的不是这张卡，而是**没把边界定下来**。定完就做了。

取数走桌面侧（前端 `fetch` 会被 CORS 拦），而这条能力本身就是 SSRF 入口 —— 尤其本应用的
CSP 正是它自己配的，**CSP 拦不住走 Rust 侧的请求**：页面一旦被 XSS 攻破，就能借这条通道
探测内网，而那正是 CSP 唯一想防的事。所以边界收在最小：

| # | 边界 | 为什么 |
|---|---|---|
| 1 | **只允许 https** | 明文一律拒绝。没有明文信道，也就没有被动嗅探与中间人改包 |
| 2 | **IP 字面量落在私有/保留网段就拒绝** | `169.254.169.254`（云实例元数据端点，拿到它等于拿到临时凭据）、`127.x`、`10/8`、`172.16/12`、`192.168/16`、`100.64/10`、`::1`、`fc00::/7`、`fe80::/10`，含 IPv4-mapped 绕法 |
| 3 | **不跟随重定向** | 3xx 原样报出。堵掉「一个看起来正常的公网 URL 302 到内网」这条最常见的绕过，也避免把请求扇出到用户没填过的 host |
| 4 | **只有 URL** | 无自定义 header、无方法可选、无请求体、不带 Cookie 与 Authorization。能力从「请求构造器」缩成「一个字符串」，可审计 |
| 5 | **导入备份时重跑校验**，不合规条目丢弃并回显数量 | 别人分享的备份不该能把内网地址带进来；丢弃数量要告诉用户，否则他只看到名单莫名少了几条 |
| 6 | 10s 超时、响应体上限 1 MiB | 挡住「指向一个无限流的大文件」把内存吃光 |

**明确不挡的：DNS rebinding。** `evil.com` 解析到 `127.0.0.1` 这种靠域名绕开的，挡不住。
理由：请求本来就是以用户身份发出的，本机任何进程都能做同样的事，边际风险很小；
而真正值得挡的是「顺手填了个内网地址」和「云元数据端点」这两类**实际会踩**的坑。
真要防就得自己解析 DNS、校验解析结果、再把 IP 钉进连接 —— 那要在 WinHTTP 上另开一条
自定义连接的路径，代价远大于收益。

**代价要说清楚**：因为第 2 条，**监控不了自家 NAS / 路由器**。这是刻意的取舍 ——
那是另一个特性、另一套边界，不该顺手塞进来。

两处实现上的坑值得记：

- **IPv6 字面量不能按冒号切**。`fc00::1` 按冒号切出来是 `fc00`，那是个**能解析成功的
  IPv4 形状**，等于「不在私网段里」—— 边界直接漏了。`fe80::/10` 还要跨字节：头字节必须是
  `0xfe` **且**第二字节高两位为 `10`，写成 `(o[0] & 0xC0) == 0x80` 会漏掉整段。
  这两处都是被单测抓出来的，不是看代码看出来的。
- **前端也判一遍边界，那不是安全边界**。前端那份是为了用户敲错时立刻有反馈；
  Rust 那份才是边界（前端能被 XSS 改，Rust 不能）。两边各判一次是有意的冗余。

### 一个必须说清的限制：这张卡不显示 HTTP 状态码

本机 WinHTTP 层查响应头这条路是坏的（`WinHttpQueryHeaders` 对各种 info level 一律返回
`ERROR_WINHTTP_SECURE_FAILURE`）。所以这张卡能回答「**通不通、多久**」，
回答不了「**是不是 404**」。显示成具体数字会是编的，所以宁可不显示。
