# 卡片目录：40 张（2026-10-04 定稿）

起因：反馈「可添加的功能卡片太少了」。目标：注册表达到 **40 种卡**。分四批落地，
每批都按同一套门禁交付（引擎单测 / 三档视口不裁字不溢出 / 最小字号 ≥11px / 尺寸契约 / 文档）。

**三条产品判准**（选卡与排批次都按这个来）：

1. **本地优先**：能本地算的不联网；联网的卡走 §10.15 的克制模式（首次渲染才查、缓存、取不到如实说）。
2. **用户写的字进 `cardData`（进备份）；偏好进各自的 key（不进备份）**。
3. **每张卡都要过"十卡同屏"那条 E2E 的口径**（不溢出、不裁字、最小字号 ≥11px）。

### 为什么没有一张卡叫「番茄钟」

番茄工作法是一套**预设值**（专注 25 / 短休 5 / 每 4 段长休 15），不是一种计时机制 ——
它的机制就是"倒计时 + 到点自动切段"，那正是「间歇计时」。给一套预设单独发一张卡，
卡片的功能承诺就超过了它实际保证的范围：用户会以为它默认 25/5、能数番茄、四个一循环，
而这些都不该由一张工作台卡片来担保。所以它是**间歇计时里的一个预设**：
要 50/10、90/15 也是改预设表的一行，不用再发一张卡。

这个判断同时也修正了本文档早先的排序 —— 原来的写法把「番茄钟」当成"最贵、最该最后做"的卡，
而实际上它是**最便宜**的：机制与倒计时共用，只差一个相位表。

### 一套机制，四种投影

四个钟共用 `RunState = { running, startedAt, accumulatedMs }`，其余全是它的投影：
正计时直接显示 `elapsed`；倒计时显示 `duration - elapsed`；间歇与呼吸是"倒计时 + 到点换一段"。

**硬纪律：不存累加计数器，存"从哪个时刻开始的"。**
`setInterval(1000)` 每秒 `acc += 1000` 在后台标签页会被节流到一分钟一次，
于是它记的时间比真实时间少一大截 —— 用户回来发现"我明明过了十分钟"。
`setInterval` 只用来重绘，不用来累加时间。

### 月度热力图：颜色是相对深浅，不是好坏

- 按**本月**最大值归一，且 max 至少为 1（不除以零）。
- **上个月的极端值不得影响本月色阶** —— 早先的写法是对整份数据求 max，
  结果是"9 月某个 99"把 10 月压成一片浅色，而界面上没有任何地方能解释这件事。
- **只有最大值为 1 时才退化成两档**（所有非零值都是 1，"填满 vs 空着"已经是全部信息）。
  `{1, 4}` 是真有两个量级，这时必须画出差。
- 未来的日子画得更淡、不上色：还没到的日子不该显示成"没打卡"。
- 图例上明写「颜色按本月相对深浅，不是好坏」。**颜色带评价色彩，
  而"这天打了三次卡"既不是好也不是坏** —— 那个评价不该由一张卡替用户下。
- 刻意**不做一整年 53 列**：那在这个工作台里会挤成一条 1px 的线，投影也救不了。

### 快捷链接：只做复制，不做打开

要在桌面壳里打开外部链接需要 `tauri-plugin-opener` —— 那是这个项目至今**唯一没引入的新依赖**，
而且它把"链接去哪"交给外部应用决定。权衡之后只做复制：不需要新依赖、行为完全可预期、
网页版与桌面版一致。代价是多一步 Ctrl+V，所以每个条目都写明"点了会复制什么"。
协议用**白名单**（http/https/mailto/ftp/obsidian/vscode/file），黑名单永远漏得掉下一个危险协议。

### 整数位计算：率的解读按数值大小，不看写法

- `>= 1` 已经是百分数（`6` = 6%），`< 1` 是小数（`0.06` = 6%），带不带 `%` 等价。
- 早先的写法是"不带小数点就乘 100"，那会把 `6` 读成 **600%** —— 在税率场景里差 100 倍，
  而界面看不出错在哪。这条是本轮测试逼出来的设计修正。
- 金额到**分**、率到**万分之一**（税点 6%、折扣 2.5%、分摊到 3 位都要四位精度）。
- 四舍五入用**财务口径（负数远离零）**而不是 `Math.round`：后者给 `-0`（往 +∞ 取整），
  那种差异会让一张退款单和一张发票对不上。
- 去率净额用**除法**而不是 `base - result`：后者会被四舍五入误差放大。

### 值班表：一条可手算的规则，不做可配置排班

可配置的排班规则（每人一条正则式）才是真正的排班系统，也是最容易出错的软件。
这一版只支持一条：**从锚点起按天序轮转，同日内按班次顺延**
（索引 = `(天数 × 每天班次数 + 班次序号) mod 名单长度`）。它覆盖绝大多数小团队的轮流值日，
而且任何一天的值都能手算验证。名单为空时显示「待排」，**不回落到第一个人** ——
那会让一张没填的表看起来像已经排好了。需要复杂规则时正解是接一个日历系统。

### 年历：等真实需求，而不是提前铺 500 个 DOM 节点

当初跳过的理由是一张年历要 500+ DOM 节点，在工作台里会掉帧。实际做下来的取舍：

- 12 个月**只在展开视图里**渲染，概览视图走 2 列摘要 —— 拖到最小尺寸时不会带着 500 个节点跑。
- 月历网格复用既有 `calendar` 的 6×7 定宽布局与月首偏移算法，不另写一套历法。
- 闰年、大小月、跨年周全部按真实日历规则算，**不假设每月 30 天**。
- `daysInMonthOf` 复用 `heatmap` 已有的那份实现。起初在年历里又写了一遍，
  被 `export *` 的重名冲突顶出来才发现 —— 大小月与世纪年只能有一套算法，
  两份迟早会走偏。世纪年（1900 平 / 2000 闰）的断言也一并搬进 heatmap 的单测。
- 不做"点某天写备注"：那要求用户先有一个能记东西的地方，而这张卡的定位是**看全年分布**。

代价是：要在年历上直接标注，还是得等便签/待办长出日期维度。所以这张卡刻意只读。

### 每日一图：卡住的不是这张卡，是"前端不能直接取数"

Bing 的 `HPImageArchive.aspx` 不返回 `Access-Control-Allow-Origin`，WebView2 的前端 `fetch`
**必然**被 CORS 拦。试过的社区接口（oioweb / thinkercn / vvhan / moing）在本机分别
TLS 失败、DNS 失败、超时 —— 依赖它们等于把一张卡做成随机故障。

正解是桌面侧取数：新增一条 Rust 命令，**桌面端用 reqwest 取回 JSON，前端只渲染**；
`<img>` 的加载本身不受 CORS 约束，所以 CSP 只需在 `img-src` 放行 bing 一个域名。

这条路这次走不通，卡在一个项目级的问题上：给 `modulo` 加上 `reqwest` 依赖后
（`Cargo.lock` 只多一行、**没有引入任何新 crate**），lib 的测试二进制在 windows-gnu 下
加载失败 —— `STATUS_ENTRYPOINT_NOT_FOUND`（0xC0000139），`cargo test` 一个测试都跑不了。
已确认是链接结果的临界跳变：同一份源码只差一个 `const &str` 的写法，
就从"能跑"变成"不能跑"，与语义无关。CI 的 Rust 门禁跑的是 `cargo test`，
所以这个改动不能就这么留下。

没有 HTTP 客户端可用之前，这张卡停在目录里。

### 网页监控：仍然没做，且是刻意的

任意 URL 的网页监控必须回答"服务器替谁去访问了这个地址"，那是 SSRF 的标准入口 ——
内网地址、云元数据端点、只在内网可达的管理页面都在射程内。真要做，正解是先有
代理 + 域名白名单 + 频率限制，而不是在面板里放一个输入框让用户填 URL 然后由桌面端去请求。
需求边界没定之前，这张卡留在目录里但不开工。
