# F-13 AI 动作：让它不只会说，还能动手（v1）

状态：**v1.1 已落地**（v1 = 第十二笔、v1.1 = 第十三笔，2026-11-09）｜实现见 §12.70 / §12.71

## 这一笔解决的是哪个问题

README 第一支柱写的是「**对话即指令**」——"说一句，它就去建那张卡、改那份数据"。
但到今天为止，AI 只会**说**：`src-tauri/src/ai/` 里没有 tool-call 面，前端也只有
`ai_chat` / `ai_chat_cancel` / `ai_summarize` 三条命令。用户说「帮我把这个月的开销记上」，
它回一段话，用户还得自己找到那张卡、自己填。

这一笔把中间那段接起来：**模型可以提议动作，用户点头，动作落到版面与数据上，全程可撤销。**

## 三条硬边界（刻意的）

1. **AI 永不直接写**。回复里带动作只是**提议**：坞里出一块「它想这么做」，列清每一步的人话，
   点「照做」才执行。AI 写用户的数据这件事，确认权必须留在人手里——这与 F2 定时任务
   「到点自动跑 = 未经确认花钱」是同一条纪律。
2. **白名单是封闭的，v1 只开三个动作**（都映射到既有写入口，因此全部进撤销栈）：

   | 动作 | 写法 | 落到哪 |
   |---|---|---|
   | `addCard` | `{"type":"addCard","moduleId":"todo","variant":"可选"}` | `store.add()`（版面历史） |
   | `todo.add` | `{"type":"todo.add","text":"…"}` | `cardDataApi.addTodo()`（内容历史） |
   | `ledger.add` | `{"type":"ledger.add","cents":1234,"category":"餐饮","note":"可选"}` | `cardDataApi.addLedger()`（内容历史） |

   **没有删除 / 清空 / 覆盖类动作** —— 破坏性动作不进 v1（要撤有 Ctrl+Z，要删有界面）。
3. **看不懂的必须说出来**。坏 JSON、未知动作、校验不过的行都收进 `bad`，界面原样列给用户看
   （"它想做「canvas.clear」这件事 —— 这一版还不会"）。静默丢一行，用户就会以为
   "它什么都没想做"——那是另一种谎言。

## 通道：为什么是文字约定而不是 tool-calling

本仓要同时伺候官方 / DeepSeek / 千问 / vLLM / Ollama / 自定义网关，而各家对**未知顶层字段**
的容忍度不同（E3 的教训：有的直接 400）。tool-calling 协议会把这条风险面放大到每一个 provider。

所以 v1 走**文字约定**：能力说明拼进 system 块（`actionPrompt()`，纯函数、逐字可测），
模型在正文之后一行一个 `@@act {json}`。解析在前端（`parseActions`），
**零 Rust 改动、零协议面**。代价是模型可能写坏 —— 所以解析宽容（围栏 / 空白 / 行中不算）、
失败可见（见边界 3）。

## 落点（纯层 / 胶水层）

- **纯层 `src/vue/aiActions.ts`**：`parseActions(text, ctx)`（剥行 + 校验 + 坏行收集）、
  `stripActionLines`（历史回填的展示口径）、`actionLabel`（人话）、`actionPrompt`（能力说明）、
  `runActions(actions, apply)`（**首败即停**，与工作流同一条纪律）。
- **胶水层**：`ChatDock.vue` 在 **done 帧**解析（不是 await —— `ai_chat` 先返回会话号）、
  渲染提议块（`data-ai-acts`）、「照做 / 算了」两个按钮；执行就是上面那张表的三个写入口。
- **`aiChat.ts`**：`buildMessages` 的 system 块 = 引用块 + 能力说明（**常驻**）；
  `turnsFromHistory` 把助手气泡里的动作行剥掉（历史里只留人话）。

## 校验与上限（都在纯层，逐条有测试）

- `addCard` 的 `moduleId` 必须在**注册表**里（`store.reg` 的 id 全表，不是提示清单）；
- 文本上限：待办 ≤200 字、分类 ≤20 字、备注 ≤200 字；**超长拒收不截断**（截断会改语义）；
- 金额是**正的整数分**（12.34 元 = 1234），上限 ¥1000 万；
- `date` 缺省今天是 `localDay` 的口径；写了看不懂的日期不执行；
- **一次最多 5 个动作**，多出来的不执行、数出来说明。

## 没做的（如实记）

- 不做 tool-calling 协议；不做删除 / 清空类动作；不做 AI 自主连跑（每一步都要点头）；
- **提议状态不落盘**：刷新之后提议块消失、历史里只剩人话正文（Rust 单点落盘的是原文，
  回填时剥行）——"历史里那些按钮点不回去"是刻意的，历史不是操作面板；
- 写入面只有上面三个（v1.1 又加了三个，见下）：便签 / 倒数日 / 习惯等的写入口当时留了后续
  —— 那一句在 v1.1 里被逐字兑现；
- `@` 引用与动作是两条独立的链：动作不需要引用卡片也能发生。

## v1.1（第十三笔）：白名单扩到便签 / 倒数日 / 习惯

三个新动作，**通道零改动**（`@@act` 格式 / 提议块 / 照做-算了 / 首败即停 / 坏行可见全原样）：

| 动作 | 写法 | 取舍 |
|---|---|---|
| `sticky.append` | `{"type":"sticky.append","text":"…"}` | **只追加、不覆盖** —— 便签是用户的原文，AI 没有整段替换的权力；text ≤200 |
| `countdown.set` | `{"type":"countdown.set","label":"纪念日","date":"2026-12-01"}` | 名字与日期**都必填**（缺名字去猜"改哪个日子"只会猜错）；label ≤20、日期 `YYYY-MM-DD`。**示例值要与 E2E 夹具错开**（能力说明整体进 system 块；初版示例写了 `发版`，撞上「@第二张卡」用例的禁用词，见 §12.71 末） |
| `habit.check` | `{"type":"habit.check"}` | 打**今天**的卡（`localDay` 口径）；**幂等** —— 今天已打过就不重复加 |

实现要点：执行姿势与倒数日 / 习惯卡自己的写入点**同一套**（`writeSticky` / `writeCountdown` /
`writeHabit` + 注入的 `cardDataApi.state`），没有新协议、没有新存储键。见 §12.71。

**v1.1 仍未开的**：删除 / 清空 / 整段替换类动作；四象限 / 速记等的写面（`addMatrixTodo` /
`addNote` 都在手上，按"最常用且语义无歧义"逐个加）；多实例的定点写 —— 动作侧还没有
`@卡片` 的等价物（`sticky.append` / `habit.check` 都作用在第一张）。

## v1.2（第十四笔）：agent 循环（工具结果回喂）

「照做」不再是终点：执行完把逐条结果拼成一条带标记的**合成 user 消息**（`（工具结果）…`）
追加进对话，并**自动续一轮** —— 模型据此继续提议（**仍需点头**）或收尾。
**循环由「确认」这件事自然限流**（每轮续跑对应一次点击，不是无限自动跑）。

协议折叠：Rust 的 `Msg` 只有 user / assistant / system 三种角色 ⇒ 结果用 **user 承载 +
文本标记**；界面按标记渲染成**工具结果小条**（不是用户气泡 —— 用户没说过这句话），
回填（`turnsFromHistory`）走同一规则。三个细节：**引用快照跟轮次走**（续轮沿用产生那批
动作的 `usedChips`，`@卡片` 上下文不丢）/ **附件不跟着走**（复用会把文件正文再发一遍）/
**首败也回喂**（失败与「因前一步失败而没执行」逐条写进结果）。见 §12.72。

**v1.2 仍未开的**：**read 类动作**（模型只能写、不能查 —— "看一眼那张卡再决定"要等下一档）；
多工具并行（一轮只有一条结果消息）；无限自治循环（刻意不做：确认就是限流器）。

## v1.3（第十六笔）：read 类（先看再动）

观察补上：`context.read`（看版面清单 / 看某张卡里的内容）提议进来，执行体**只取不写**，
看到的内容**随执行结果回喂给模型**（`RunResult.values` 通道）—— 模型下一轮能据此再提议。

**刻意保守的三点**：
1. **读跟着写一起走确认**：read 与写动作挂在同一个提议块里，一次「照做」把可读的都读了、
   该写的都写了，结果一起回喂 —— 零新增往返成本，也没有"为读单独建一个确认层级"的
   复杂性（那是给会自己发请求的模型准备的）。将来若做「读不走确认」的第二档（仅读自动执行、
   有轮数上限），再说；
2. **读的内容有上限**：单条回喂 ≤200 字，摘录口径与 `@卡片` 同一套（`excerptFor`），
   先由它定上限（400），胶水再截一次；
3. **看哪张卡 = registry 白名单校验**：无 `moduleId` 看版面清单；有则过注册表；
   未知 id 整行拒收。

**v1.3 仍未开的**：多卡并行读（一轮一条结果消息）；看之前先筛选/搜索（清单较大时先检索）
—— 随"读"的需求长出来再加。（多实例定点已在 v1.4 补上，见下。）

## v1.4（第十八笔）：多实例定点 —— 指名道姓写到那一张

v1.3 补上了"看"，但写侧仍默认作用在第一张实例：动作都只认 **module id**，版面上同一模块
开多张实例时（F-01 起就有这能力），AI 没法说"往第二张习惯卡上打卡"。`sticky.append` /
`habit.check` 都作用在第一张，多开实例的定点写留到这一档补。

v1.4 给六个动作各加一个可选 `instanceId`（板上 item 的 id，如 `habit:2`）：

| 动作 | 写法 |
|---|---|
| `todo.add` / `ledger.add` / `sticky.append` / `countdown.set` / `habit.check` | 在原有参数外加 `"instanceId":"habit:2"` |
| `context.read` | `"moduleId":"habit","instanceId":"habit:2"` —— 两者必须指向同一张卡 |

**刻意保守的三点**：
1. **缺省逐字不变**：`instanceId` 可选，缺省 = 第一实例，与既有可选字段同形状；不给它的
   动作行为与 v1.3 一字不差（既有测试零改动即证）；
2. **校验全在纯层**：`instanceId` 必须在 `ActionContext.instances`（胶水层从版面 items
   解析出的清单）里，未知 id 整行拒收并说人话；`context.read` 的 `moduleId` 与
   `instanceId` 必须互相对得上，对不上也拒收 —— 纯函数逐字可测；
3. **只定点、不新增动作**：`addCard` 不加（摆卡本来就是造新实例），`memory.add` 不加
   （记忆是全局的，没有实例概念）；`ActionContext.instances` 本身可选（旧 ctx 对象
   照常通过类型检查）。

胶水层把 `instanceId` 解析成板上 item 的 module + instance，走**既有写入口**
（`cardData` 的 moduleId/instanceId 重载）—— 第二实例的数据落在 `byInstance` 切片、
整片替换 ⇒ Vue 深监与防抖落盘照旧；执行层找不到这个 id（板刚被改过）时如实报错，
不静默写去第一张。`context.read` 的版面清单从此带上每张卡的实例 id，模型"抄 id"即可。

**v1.4 仍未开的**：多卡并行读（一轮一条结果消息）；看之前先筛选/搜索（清单较大时先检索）；
按标题模糊定点（`instanceId` 只能从 `context.read` 的清单里抄 id，不做自然语言猜卡）。

## v1.5（第十九笔）：读侧增强 —— 一次读多张卡 + 读全卡

v1.3 补上「看」、v1.4 补上「指名看哪张」，但读这一档还留着两个口子（v1.3/v1.4 的「仍未开」都记着）：
① **多卡并行读**：读 N 张卡要发 N 行动作，占 N 个槽位（一轮上限 `ACTION_MAX_PER_REPLY` = 5），
回喂是 N 条结果行；② **读得太浅**：单条摘录封顶 `ACTION_READ_MAX` = 200 字，长速记 / 长清单
看不到全文 —— 而「看一眼那张卡写了啥」正是读这一档存在的理由。

`context.read` 再加两个可选参数：

| 参数 | 写法 | 语义 |
|---|---|---|
| `moduleIds` | `["todo","habit","ledger"]` | 一次读这组卡（≤ `ACTION_READ_MULTI_MAX` = 5），回喂**一条**结果消息 |
| `full` | `true` | 读全卡不截断（上限 `ACTION_READ_FULL_MAX` = 2000 字）；默认仍 200 字摘录 |

**刻意保守的四点**：
1. **缺省逐字不变**：不给这两个参数时，`context.read` 与 v1.4 一字不差（既有测试零改动即证）；
2. **互斥写清**：`moduleIds` 与 `moduleId` / `instanceId` 互斥（一组卡 vs 一张卡，混写不知道读哪个）；
   `full` 只对「读卡内容」有意义，配 roster（看清单）一律拒收；
3. **校验全在纯层**：每个 id 过注册表白名单、数量 ≤ 5、重复 id 拒收 —— 逐条人话、整行拒收
   （同 v1.4 的「不接受猜」）；
4. **上限仍要有**：`full` 不是无界读 —— 2000 字封顶，超了截断并在末尾注明全卡字数
   （回喂会进会话历史，无界读等于让模型上下文被一张卡撑爆）。

**人话**：多卡 = 「看一眼 3 张卡（待办、习惯、记账）」；全卡 = 「看一眼整张「速记」」。

**v1.5 仍未开的**：看之前先筛选/搜索（`query` 参数）；按标题模糊定点（仍然拒绝猜卡）。

## v1.6（第二十笔）：按内容找卡 —— `context.read` 加 `query`

v1.5 把「读」做厚了（多卡 + 全文），但读之前那一步还是全量看：模型要么看整份版面清单
（有哪些卡），要么按 `moduleId` 一张张读。版面上卡一多，「哪张卡写了『体检』」这种问题
它答不了 —— 只能一张张读，一轮还最多 5 个动作。

`context.read` 加一个可选 `query`：

| 参数 | 写法 | 语义 |
|---|---|---|
| `query` | `"体检"` | 在版面上**找内容（或卡名）里含这个关键词的卡**，回喂**一条**结果消息 |

**刻意保守的四点**：
1. **找卡 vs 读卡互斥**：`query` 与 `moduleId` / `moduleIds` / `instanceId` / `full` 互斥
   —— 一个是「搜索」，一个是「读这一张」，混写不知道要哪个；
2. **匹配卡名 + 全文**：卡名对得上也算（清单里能看见标题）；内容取 `fullContentFor`
   （与 v1.5 的全卡取数同一份），大小写不敏感；
3. **回喂有上限**：最多 `ACTION_SEARCH_MAX` = 5 张匹配卡（超了明说「另有 N 张没列」），
   每张给关键词**前后各 40 字**的一小段（不整卡倒出来 —— 找卡是为了定位，不是读完）；
4. **无匹配要说出来**：「版面上没有写到「体检」的卡」—— 不静默返回空。

**人话**：「找一找写有「体检」的卡」。

**v1.6 仍未开的**：按标题模糊定点（仍然拒绝猜卡 —— 那是「写哪张」的问题，与「找哪张」不同）。

## v1.7（第二十一笔）：找我的东西 —— 多关键词 + 范围扩到资料 / 技能

v1.6 的 `query` 有两个欠口：① **只认一个词** —— 「体检 挂号」这样两个词一起给，
要么当整串匹配、要么匹配不到；② **只搜卡片** —— 可用户的内容早已分三类
（卡片 / 资料 / 技能，见 PR-F1 / PR-F3），「哪份资料写了 X」「我那个技能里怎么说的」
它答不了。

v1.7 把「找」补齐：

| 变化 | 写法 | 语义 |
|---|---|---|
| 多关键词 | `"query":"体检 挂号"` | 空格分隔 1–4 个词，**全部命中**才算（AND） |
| 范围扩三类 | 同上 | 卡片内容 + 资料正文 + 技能正文；命中行标出来源 |

**刻意保守的四点**：
1. **AND 不 OR**：都要出现才命中 —— 找东西是为了缩小范围，OR 只会把噪音放进来；
2. **词数上限 4**：再多就该拆成几次找（也防着模型把整段话塞进来）；
3. **单份来源仍只给一小段**：关键词前后各 `ACTION_SEARCH_RADIUS` = 40 字；
   来源名进前缀（`资料「…」` / `技能「…」` / 卡名），模型一眼知道去哪类里找；
4. **上限不变**：最多 `ACTION_SEARCH_MAX` = 5 条，超了明说「另有 N 条没列」。

**人话**：「找一找写有「体检 挂号」的东西」。

**v1.7 仍未开的**：把资料 / 技能也列进 `context.read` 的**版面清单**、以及**单读**某一份
资料 / 技能（现在只能搜到片段，要读全文仍需用户 `@`）；按标题模糊定点（仍然拒绝猜）。
